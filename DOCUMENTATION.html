Project X — Technical Engineering Documentation Report

Candidate: M. Rajiv  |  Project: Project X (Photo Drive Logger)  |  Stack: React (Vite) + Node.js (Express) + Google Drive & Sheets API

1. Executive Summary & App Overview

Project X is a production-style, lightweight web application built to fulfill all requirements specified in AGENTS.md. It allows users to authenticate via Google OAuth 2.0, automatically creates and manages a dedicated Google Drive folder named after the user, uploads geotagged photos with multi-part streaming, extracts GPS EXIF data client-side, logs coordinates to an auto-created Google Sheet, presents a responsive gallery with authenticated thumbnails, plots coordinates on an interactive Leaflet map, and shares photos with Google accounts (specifically tested with su1@vr2.in).

4. Google API & Authentication Setup

  • OAuth 2.0 Code Flow: Frontend uses @react-oauth/google with postmessage redirect. The authorization code is sent to the backend, which exchanges it for access and refresh tokens.
  • OpenID Connect Profile Decoding: Extracts name, email, and picture directly from the cryptographically verified ID token without requiring the Google People API.
  • Drive Folder Auto-Creation: Searches for existing folder named M. Rajiv before creating. Never duplicates folders.
  • Google Sheets Logging: Auto-creates GPS Log spreadsheet and appends coordinates: Photo Name | Drive Link | Latitude | Longitude | Timestamp.

5. Security & Least-Privilege Design

  • Restricted Scope: Uses https://www.googleapis.com/auth/drive.file. The app can only see and edit files it creates. Personal user files in Drive are completely inaccessible.
  • Backend Secrets Isolation: GOOGLE_CLIENT_SECRET is kept strictly on the backend. No credentials leaked to frontend bundles.
  • No Public Links: Sharing uses Google Drive Permissions API (type: 'user', role: 'writer'). Files are never publicly exposed.
  • In-Memory Tokens: Tokens reside only in React runtime state and are never written to unencrypted storage (localStorage).

6. Engineering Standards Compliance

This section provides concrete, verifiable evidence from the codebase demonstrating strict compliance with the core engineering standards mandated in AGENTS.md Section 4.

1. No Hardcoding

  • Zero Hardcoded Secrets or IDs: No client IDs, client secrets, redirect URIs, spreadsheet IDs, folder IDs, or port numbers exist as hardcoded literals in code. All configuration values are injected via environment variables (process.env in backend/src/config/googleClient.js lines 22–34 and import.meta.env in frontend/src/services/api.js line 3).
  • Dynamic Folder Naming: The Google Drive folder is named dynamically at runtime from the authenticated Google user profile (data.name in backend/src/services/driveService.js lines 32–37).
  • Documented Literal Fallback: The single literal string 'ProjectX-Photos' in driveService.js line 41 is a documented defensive fallback used solely when Google's profile API returns an empty display name. Lines 78–96 contain migration logic to rename any legacy 'ProjectX-Photos' folder to the user's actual profile name, preventing duplicate folders.

Both package.json files contain only the strictly necessary packages:

  • Backend (backend/package.json):

    • googleapis (^140.0.1): Official Google Node.js client for OAuth2, Drive v3, and Sheets v4.
    • multer (^2.4.0): In-memory buffer stream handler for uploads directly to Google Drive.
    • Audited: axios was verified as unused and uninstalled via npm uninstall axios.

3. Production-Style Architecture

Clear separation of concerns across dedicated architectural layers:

  • backend/src/config/: googleClient.js encapsulates OAuth2 client instantiation and token injection.
  • backend/src/routes/: Route handlers (auth.js, drive.js) handle HTTP request/response lifecycles only.
  • backend/src/services/: Business logic (driveService.js, sheetsService.js) for folder deduplication, file streaming, sheet row appending, and in-session caching.
  • frontend/src/context/: AuthContext.jsx manages user session and in-memory token state.
  • frontend/src/services/: Network clients (api.js, driveService.js) isolating HTTP calls from UI components.
  • frontend/src/utils/: Pure helper utilities (fileUtils.js, exifUtils.js).
  • frontend/src/components/: Focused presentational components (Gallery.jsx, PhotoCard.jsx, UploadButton.jsx, MapView.jsx).
  • frontend/src/pages/: Page orchestrators (LoginPage.jsx, Dashboard.jsx).

4. Validation

  • Client-Side File Validation (frontend/src/utils/fileUtils.js lines 10–26): Validates file existence, allowed MIME types (image/jpeg, image/png, image/webp, image/heic, image/heif), and max size (≤ 20 MB) before network transfer begins.
  • Server-Side File Validation (backend/src/routes/drive.js lines 21 & 66–68): Multer limits size to 20 MB and handler verifies req.file exists.
  • Sharing Email Validation: Client-side HTML5 validation and .trim() in PhotoCard.jsx line 110; server-side regex/format check (!emailAddress || typeof emailAddress !== 'string' || !emailAddress.includes('@')) in backend/src/routes/drive.js lines 140–142.

5. Error Handling & Information Hiding

  • Try/Catch on Every Route: All asynchronous route handlers wrap Google API invocations in try/catch blocks.
  • Information Hiding: Internal stack traces and raw Google API error payloads are logged server-side only via console.error. Users receive safe, friendly messages.
  • Global Fallback Error Handler (backend/src/index.js lines 28–34): 
    app.use((err, _req, res, _next) => {
  console.error('[server] unhandled error:', err.message ?? err);
  res.status(500).json({ error: 'An unexpected error occurred.' });
});

6. Clean Code

  • Zero Leftover Debug Logs: No temporary console.log() statements remain in production code. Only the deliberate server startup log exists in backend/src/index.js line 37.
  • High-Value Comments: Comments explain non-obvious engineering decisions (e.g. token exchange idempotency, singleton protection, streaming without temporary disk files, and OpenID Connect decoding) rather than restating obvious syntax.

7. Optimization & API Efficiency

  • In-Session Folder & Sheet Caching: Uses in-memory Map caches (_folderCache and _sheetCache) to eliminate repeated Drive search API queries.
  • Parallel Fetching: Executes Drive photo list and Sheet metadata queries simultaneously via Promise.all.
  • Zero Memory Leaks: Object URLs generated for authenticated thumbnails are revoked upon component unmount via URL.revokeObjectURL().
